Solution projection and power-flow comparison

After independently checking a solution, use this workflow to compare its predicted state with a re-solved power flow. project_solution pins supported dispatch and tap decisions onto a copy of the network. Comparing that snapshot in BMOPFTools and an external engine can help investigate discrepancies, subject to the conversion coverage below.

Prerequisites: a solved case, BMOPFTools, JuMP and a suitable optimizer. The BMOPF comparison needs no external dataset; the additional OpenDSS comparison requires OpenDSS and a supported export. The file-based code below is a workflow template, not an example executed during the docs build. For the package's test fixtures and coverage, see engine validation.

The idea: pin the solution, re-solve as a determined power flow

An OPF can choose generator/IBR dispatch, transformer taps and inverter setpoints. Pinning the supported decisions to their solved values produces a snapshot for a power-flow comparison. Check that the projection recorded every intended device and that the case has valid references; pinning dispatch does not establish uniqueness of the power-flow solution or cover arbitrary custom controls. Missing or nonfinite dispatch records can leave a device unpinned.

project_solution(net, result) does exactly this pinning and returns a deep copy of net (the input is never mutated):

  • Generators and IBRs — per-phase active/reactive dispatch is frozen to the solved values (p_min == p_max == pg, q_min == q_max == qg). An IBR running a Volt-var / power-factor control_profile has the profile dropped and explicit fixed bounds written, freezing the smart-inverter control at its solved operating point (the profile couples Q to P internally, so pinning both fixes it).
  • Free transformer taps — a tap that was an OPF decision variable (reported as tap / tap_ratio in the result) is written back onto the winding. Fixed-tap transformers are left untouched.

The projected network can be passed to solve_pf, and exported for comparison where to_dss supports the represented model. net_projected["_meta"]["projection"] on the returned network records what was pinned (generators, ibrs, control_profiles_frozen, free_taps) so a later oracle mismatch can be attributed.

The three-way triangulation

With a determined snapshot in hand there are three computational routes to the same voltages. Only route C uses an external engine; comparing all three still helps localise disagreements:

SourceWhat it is
Aresult["bus"]the OPF's own predicted voltages
Bsolve_pf(project_solution(net, result))BMOPF re-solving the pinned snapshot as a power flow (self-consistency check, not an independent oracle)
COpenDSS solving to_dss(...) of the snapshotan external engine (independent implementation comparator, not ground truth)

Reading the pattern:

  • A ≈ B provides self-consistency evidence for the projected case within the checked quantities and tolerances. A discrepancy calls for inspection of the projection, controls, references, residuals and selected solution branch.
  • A ≈ B ≉ C motivates checking export fidelity and conventions, as well as numerical tolerances and solution-branch differences. It does not by itself identify which implementation or model assumption is responsible.

The A/B comparison uses the package's own engine. The C comparison uses an independent implementation and must account for to_dss fidelity warnings and coverage. Check the returned warnings and inspect whether the exported case represents the intended controls, references and devices before comparing voltages.

Exporting the dispatch to OpenDSS — dispatch_as_loads

When exporting a pinned dispatch as fixed PQ loads is appropriate, dispatch_as_loads provides that representation: it rewrites every pinned generator/IBR as an equivalent constant-power negative load (p_nom = -p_min, q_nom = -q_min) — carrying the device's terminal map and connection. A fixed PQ injection is a negative constant-power load, so under the determined power flow the two forms are equivalent (solve_pf agrees to $\sim\!10^{-6}$ V). Generation sitting on a voltage_source bus is dropped, not converted — the slack source is the reference injector in a power flow and its dispatch must not be re-imposed as a load. This representation checks the pinned injection; it does not preserve the original device's control law or dispatch flexibility.

Putting it together

net    = from_dss("my_feeder.dss")
result = solve_opf(net)                    # your OPF solution

snap   = project_solution(net, result)     # pin every setpoint → determined snapshot
res_B  = solve_pf(snap)                     # B: BMOPF self-check  (expect A ≈ B)

deck   = dispatch_as_loads(snap)            # generators/IBRs → negative loads
export_warnings = to_dss(deck, "snap.dss"; allow_unverified_ratings=true)  # inspect before running OpenDSS
# Run the exported deck in OpenDSS and align terminal names, units and references
# before comparing its voltages with result and res_B.

The comparators used in the test suite (test/roundtrip_helpers.jl) apply the same node-name bridge and skip tolerance (|V| < 1e-4 earth/neutral nodes) as the engine feasibility harness, so the projection cross-check reuses the OpenDSS comparison method verbatim — the only new machinery is the pinning. test/projection_tests.jl runs this on DER-augmented feeders and free-tap fixtures (the raw pf_comparison cases have no decision variables, so projection is a no-op there).
